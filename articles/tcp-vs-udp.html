Beginner Path · 005

TCP vs UDP

Two devices need to communicate. But they don't always need to communicate in the same way.

So far, we've followed a request quite a long way.

We started with a website name.

DNS helped us find an IP address.

The IP address helped identify the destination.

A port helped identify the service we wanted to communicate with.

It feels like we finally know where we're going.

But there's another question hiding underneath all of this.

One more thing

Once two devices know where to communicate, how should they actually exchange the data?

Imagine sending something important

Imagine you need to send a package containing an important document.

You have two choices.

With the first method, you want the delivery system to keep track of the package, make sure it arrives, and notice if something goes wrong.

With the second, speed matters more. You send the information and don't want to spend extra time checking every part of the delivery.

Both approaches can be useful.

Networking has a similar choice.

Two important transport protocols you'll encounter are TCP and UDP.

TCP wants to know what happened

Imagine you're sending ten pages of a document.

You don't just want the pages to arrive.

You want to know that they arrived, that they're in the right order, and that missing pages can be dealt with.

That's the basic idea behind TCP.

TCP is designed to provide reliable, ordered delivery of data between applications.

Before TCP begins sending application data, the two sides establish a connection.

During communication, TCP keeps track of the data being exchanged and uses acknowledgements and retransmissions to help deal with missing information.

So if something goes missing, TCP has mechanisms for detecting and recovering from that problem.

And then there's UDP

Now imagine you're watching a live video.

A tiny piece of data gets lost.

You probably don't want the entire stream to stop while everyone waits for that missing piece to be sent again.

You'd rather keep the stream moving.

That's the kind of situation where UDP can make sense.

UDP is a connectionless transport protocol that sends datagrams without providing TCP's built-in reliability and ordering.

UDP doesn't establish a TCP-style connection before sending data.

It also doesn't provide the same built-in mechanisms for acknowledging and retransmitting lost data.

That makes it simpler and can reduce overhead, but the application has to handle reliability itself if it needs it.

So which one is faster?

This is where the usual beginner explanation can become misleading.

You might hear:

“TCP is slow and UDP is fast.”

That's too simple.

UDP has less built-in overhead because it doesn't provide TCP's connection setup, acknowledgements, ordering, and retransmission mechanisms.

But whether an application is actually faster depends on the network, the application, the amount of data, latency, congestion, and what the application is trying to accomplish.

The more useful question isn't: “Which protocol is faster?”

It's: “What does this application need?”

Neither is simply “better.”

They're designed around different communication needs.

You've already seen both

Remember the ports from the previous article?

A port number by itself doesn't tell the entire story.

The transport protocol matters too.

For example, a service can be associated with a TCP port, while another service can use UDP.

Same idea, different transport
Application → TCP → IP
Application → UDP → IP

This is one reason you'll often see things written like TCP/80 or UDP/53.

The number identifies the port, while TCP or UDP tells you which transport protocol is being used.

Why should cybersecurity people care?

Now imagine you're looking at a network capture or a security alert.

You see traffic involving:

Example traffic
10.0.0.15 → 10.0.0.20:443 TCP
10.0.0.15 → 10.0.0.1:53 UDP

Knowing whether traffic uses TCP or UDP gives you another piece of the puzzle.

A SOC analyst may encounter TCP connections in logs, UDP traffic in packet captures, or unusual patterns involving either protocol.

During network reconnaissance, security tools may also report different results depending on whether you're examining TCP or UDP ports.

So this isn't just networking theory.

It's part of learning how to read what is happening on a network.

But there's a trade-off

TCP's reliability is useful, but it comes with additional communication.

UDP's simplicity can be useful when an application cares more about continuing communication than recovering every lost packet.

That's why different applications can make different choices.

A file transfer generally cares deeply about receiving the correct data.

A real-time application may care more about keeping information flowing with low delay.

The protocol choice follows the problem the application is trying to solve.

And now our journey has another layer

Look at everything we've discovered so far.

Following a request
Website name → DNS
IP address → Destination
Port → Service
TCP / UDP → How data is transported

What started as:

“I typed a website address.”

has turned into a chain of systems working together.

And we're still not finished.

Remember this

TCP focuses on reliable, ordered communication. UDP keeps transport simpler and leaves reliability to the application when needed.
