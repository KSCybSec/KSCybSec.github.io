Beginner Path · 008

What Happens When You Visit a Website?

You type a name. You press Enter. A page appears. But behind those few seconds is an entire journey.

Let's do something simple.

Open your browser.

Type:

https://example.com
YOU PRESS ENTER

And then…

something starts happening.

From your point of view, the whole thing feels almost instant.

But your browser can't simply shout “Give me example.com!” into the Internet and hope someone answers.

There is a process.

And now you already know most of the pieces.

Let's follow the request

Browser
→
DNS

Web Server

Don't worry if that looks like a lot.

We've already met almost every part of this journey.

Now we're simply putting the pieces together.

Step 1 — Your browser needs an address

You typed:

https://example.com

Humans like names.

Computers communicating across networks need addresses.

So the browser needs to discover the IP address associated with the domain name.

That's where DNS comes in.

Your device asks a DNS resolver for the address associated with the domain.

If the answer is available, the browser now has a destination to contact.

Think about it: before your browser can ask a server for a webpage, how would it know which machine to contact?

That's one reason DNS matters.

Step 2 — Now it knows where to go

The browser has an IP address.

Something like:

93.184.216.34

Now the request has a destination.

But there's another question.

Which service on that machine are we trying to reach?

That's where ports enter the story.

For normal web traffic, you'll commonly encounter:

HTTP → port 80
HTTPS → port 443

So now we have something much more specific:

“I want to communicate with this IP address, using this web service.”

Step 3 — The data has to travel

Finding the destination isn't enough.

Your request still has to travel across networks to reach it.

This is where the concepts of networking and transport become important.

For a typical HTTPS connection, TCP is involved in transporting the data reliably, while TLS provides protection for the application communication.

You don't have to understand the entire TLS handshake yet.

For now, think of it as the beginning of a protected conversation between your browser and the server.

The browser isn't just sending information blindly. It is establishing the communication it needs before exchanging protected web data.

Step 4 — The server finally hears from you

Your request has reached the web server.

Now the server has a job.

It needs to understand what you asked for.

Maybe you requested the homepage.

Maybe you requested an image.

Maybe your browser is asking an application for some data.

HTTP provides the rules for that conversation.

The browser sends a request. The server processes it. Then the server sends a response.

Step 5 — The server sends something back

Suppose everything went well.

The server responds with the requested information.

HTTP/1.1 200 OK

Here's the content you requested.

Your browser receives the response.

But a webpage is rarely just one file.

The HTML might tell the browser to load CSS. The CSS might reference images. JavaScript might request additional data.

So your browser may make many more requests before the page is fully displayed.

That beautiful webpage you see could actually be the result of a whole series of conversations.

And then you see the page

After receiving the necessary resources, the browser processes them and builds the page you see.

You see a website.

It feels like one action.

But underneath it was more like this:

01
You enter a domain name

The browser needs to figure out where that name leads.

02
DNS helps find an IP address

The domain name is translated into an address the network can use.

03
The browser connects to the destination

The connection reaches the relevant service, commonly through port 80 for HTTP or 443 for HTTPS.

04
The browser sends a request

HTTP defines how the web request and response are structured.

05
The server responds

The server sends back the requested content or an appropriate response.

06
Your browser builds the page

The browser processes the returned resources and displays the website.

Now imagine something goes wrong

This is where the whole journey becomes interesting from a cybersecurity perspective.

What if the DNS answer is manipulated?

What if the destination is not the one you expected?

What if an exposed service is vulnerable?

What if someone sends you a convincing link to a fake website?

What if the server itself has been compromised?

Suddenly, all the concepts we've learned stop looking like isolated networking vocabulary.

They become pieces of an investigation.

A security analyst isn't just looking at “a website.” They're looking at the chain of events that made the website reachable, communicated with, and trusted.

And that chain leaves clues

This is one of the most useful ideas to carry forward.

Every step can produce information.

DNS queries can appear in logs. IP addresses can appear in network traffic. Ports can reveal exposed services. HTTP requests can appear in web logs. TLS certificates provide information about a service.

Security tools can observe parts of this journey.

A network analyst might inspect packets.

A SOC analyst might investigate an unusual connection.

A penetration tester might enumerate exposed services.

An incident responder might reconstruct what happened after an attack.

Different roles.

Same underlying trail.
