HTTP vs HTTPS

Your browser has found the server. Now something else has to happen: they need to communicate.

In the last article, we followed a domain name through DNS and eventually reached an IP address.

Then we learned about ports.

So imagine we're back at that moment.

Your browser has found the destination.

But now it has to ask for something.

Maybe a webpage. Maybe an image. Maybe some data.

And the server needs to know what the browser is asking for.

This is where HTTP enters the story.

So what is HTTP?

HTTP stands for Hypertext Transfer Protocol.

Don't let the name make it sound more complicated than it is.

Think of HTTP as a set of rules that helps a browser and a web server communicate.

The browser makes a request. The server processes it. Then the server sends a response.

Browser
→ request →
Web Server
→ response →
Browser

That's the basic idea behind a huge amount of what happens when you use the web.

What does a request look like?

You don't normally see it happening.

You type a website address, press Enter, and your browser handles the communication for you.

Underneath that simple action, the browser can send an HTTP request asking the server for a resource.

GET /index.html HTTP/1.1 Host: example.com

You don't need to memorize that yet.

The important idea is simply: the browser is asking the server for something.

The server then sends a response.

HTTP/1.1 200 OK <html> ... </html>

The browser receives that response and uses it to build what you see on the screen.

And sometimes the answer is not “yes.”

A server doesn't always return the page you asked for.

Maybe the page doesn't exist.

Maybe the server encountered a problem.

That's where HTTP status codes become useful.

Code
Meaning
200
The request succeeded.
404
The requested resource wasn't found.
500
The server encountered an error.

These codes are incredibly useful when troubleshooting websites, investigating applications, or looking at security logs.

But there's a problem with plain HTTP.

Imagine you're sending a letter.

The letter reaches its destination, and the communication works.

But what if someone along the way could read what was written inside?

That's one of the problems HTTPS is designed to address.

Think about this: If you were entering a password on a website, would you want that password traveling across the network in a form that an observer could simply read?

Obviously not.

This is where the extra S becomes important.

HTTPS adds protection

HTTPS stands for Hypertext Transfer Protocol Secure.

At a high level, HTTPS uses TLS to protect the communication between your browser and the server.

TLS helps provide three important properties:

Confidentiality — other people on the network should not be able to simply read the protected data.

Integrity — the communication should not be silently modified while traveling between the browser and server.

Authentication — the browser can verify information about the server through its digital certificate.

You don't need to understand every cryptographic detail yet.

For now, remember the bigger picture:

HTTPS doesn't change the fact that your browser is talking to a web server. It adds a protected way for that conversation to happen.

So HTTP and HTTPS aren't two completely different worlds

They both support communication between web clients and servers.

The important difference is how that communication is protected.

Notice something important here.

HTTPS protects the connection. It does not automatically make the website trustworthy.

Wait. Then what does the padlock actually mean?

You've probably seen the padlock icon in your browser.

It's easy to interpret that symbol as:

“This website is safe.”

But that's not what HTTPS guarantees.

A phishing website can use HTTPS too.

The connection between you and that phishing site can be encrypted while the site is still trying to trick you.

HTTPS helps protect the communication channel. It doesn't decide whether the person on the other end has good intentions.

So if a suspicious login page uses HTTPS, should you automatically trust it?

No.

You still need to look at the domain, context, certificate information, page behavior, and other clues.

Now think like a security analyst

Imagine you're investigating an incident.

A user says:

“I clicked a link in an email and entered my password.”

That's already interesting.

You might want to know:

What domain did the link point to?

Was HTTPS being used?

What IP address did the domain resolve to?

What requests did the browser make?

What happened after the credentials were submitted?

Suddenly, all those concepts we've been learning start connecting.

Domain → DNS → IP → Port → HTTP/HTTPS → Request → Response

That's the beginning of understanding web traffic from a security perspective.

And this is where the story gets bigger

At the beginning of this path, visiting a website seemed almost instantaneous.

Type a name.

Press Enter.

Page appears.

But now we can see the trail underneath it.

Your browser needs a destination.

DNS helps find it.

An IP address identifies where network traffic should go.

A port identifies the communication endpoint.

TCP or UDP provides the transport.

And HTTP or HTTPS defines how the browser and web server communicate.

What looked like one simple action is actually a chain of events.

Remember this

HTTP lets browsers and web servers communicate. HTTPS adds TLS protection to that communication.
